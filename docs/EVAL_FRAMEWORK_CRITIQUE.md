# 🤔 深度反思：Project Compass 五层测评架构的由来与局限性审视

> **核心追问**：L1–L5 这五层测评架构是如何定义出来的？它真的完全合适吗？有哪些结构性盲区？

---

## 一、 它最初是怎么被定义出来的？

这套五层架构（详见 `docs/EVAL_FRAMEWORK.md`）并非凭空拍脑袋，而是由 MiniMax-M3 根据 Project Compass 的**三条核心产品承诺**逆向推导出来的：

1. **不编（No Hallucination）** ➔ 推导出了 **L2 抽取契约**（必须带精确原文引用）与 **L3 证据有效性**（不能引用不存在的证据）；
2. **不越权（No Silent Promotion）** ➔ 推导出了 **L1 两层真相隔离** 与 **L5 对抗准入拦截**；
3. **不失忆（No Amnesia）** ➔ 推导出了 **L3 检索可达性与问答** 与 **L4 跨模块 AST 调用链追踪**。

**它的设计亮点（为什么在第一阶段很有用）**：
- **因果对齐管线**：L1（存）➔ L2（抽）➔ L3（搜/答），恰好对应真实数据流，方便做归因排查；
- **裁判与选手分离**：金标准独立于系统输出，打分用确定性规则，防止大模型自己给自己打高分。

---

## 二、 冷静审视：它真的完全合适吗？（五大结构性盲区）

如果把这套架构当成长期的“唯一真理”，它存在 **5 个明显的架构缺陷与错位**：

### 1. 静态快照测评，缺失“时间轴与状态演进”
现实中的 Project Compass 是**多轮动态的**：Agent 提议 ➔ 人类批红采纳 ➔ 代码继续修改 ➔ 旧证据过时（`stale` / `superseded`）或产生新旧冲突。
但当前的 L1–L5 测的是**一次性静态快照**：
- 主语料 `easy-course-picker` 里甚至**连一条真实冲突都没有**，导致 L1/L2 的冲突指标全部空洞通过；
- 完全没有测试“人类点击采纳/驳回/要求补证”之后，系统后续会话的状态流转是否正确。

### 2. Project Compass 2.0 的核心能力在这套体系里“完全隐身”
我们在 Module 2（流式增量引文校验 + 10px 邻近预取）和 Module 3（后台静默投机沙箱 + `✦ 单测已验证`）里做了大量核心工作，但**在当前的 L1–L5 中没有任何一层在测它们**。
哪怕沙箱在测试失败时疯狂弹窗骚扰人类，L1–L5 报告依然全绿。

### 3. L4（契约层）与主链路（L1–L3）割裂
L1/L2/L3 测的是“对话 ➔ 事实 ➔ 问答”，而 L4 测的是代码库的 `code_index` 调用链。两者目前是**两张皮**：L4 没有去测“对话里敲定的架构事实”与“代码库实际 AST 变更”之间的一致性校验（例如事实约定用 Session，代码却被改成了 JWT）。

### 4. L3 的字面规则打分存在“误杀与误放”
`scorers.py` 依赖 `required_terms` 字面命中：
- 如果回答器用等价的同义表述答对了，规则会冷酷地判错；
- 如果回答器把几个关键词生硬拼在一起、逻辑完全错误，规则反而可能判对。

### 5. L1 与 L5 职责存在部分重叠
L1 的 `no_unconfirmed_promotion` 与 L5 的 `no_promotion_under_attack` 在静态离线跑测下测的是相似的防越权能力，真正的对抗差异需要靠更丰富的攻击负载（如诱导性的上下文注入、伪造 reviewer 身份字段等）才能拉开差距。

---

## 三、 务实的结论：怎么看待与使用它？

- **短期（当前阶段）**：它作为**“第一版诊断脚手架”**是合格且有价值的——只要先把 `HANDOFF_TO_AGY_EVAL_REVIEW.md` 里那些“假绿/自证/空答案满分”漏洞补上，它就能准确指导我们修好 L2 抽取和 L3 检索的短板。
- **长期（后续演进）**：不能把它供奉成神主牌，需要补齐**动态多轮冲突语料**、把 **Module 2/3 的静默沙箱与流式校验** 纳入测评层，并让 **L4 真正串联起“事实与代码”的契约校验**。
